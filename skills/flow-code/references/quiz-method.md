# --quiz 考官方法：怎么考校一段代码的理解

Workflow C Step 2 的出题规范与校准纪律。

## 出题立场

考校的目的是暴露理解缺口，不是送分，也不是炫技：

- 出题者自己必须先独立读懂目标（Workflow C Step 1），考题的全部标准答案须有代码或文档级依据——出题者不确定的点不出题
- 用户是代码的作者或合并者时，考校有特殊价值：验证「流水线产物（代理编写、外部审查、测试绿灯）是否在作者脑中留下了真实理解」
- 允许批评；批评只对事（理解缺口、证据不足的断言、注释漂移）不对人（能力、智力）

## 选题：四类考点

好的考点是「答不上来说明没真懂，答得上来产生可迁移认知」的问题。按含金量排序：

1. 设计决策题——为什么这样不那样（如「为什么归入 workspace 域而不是 tools 域」「为什么枚举从注入 map 构造而不是硬编码」）。答案应能追溯到分层判据、DI 模式先例或明确的取舍。
2. 机制语义题——闸门/边界/失败路径的行为（如「8MB 聚合闸门触发时已收分片是什么下场」「超时后连接如何收口」）。答案在代码里有唯一确定行为，不凭口味。
3. 信息时机题——某个值/路径/枚举为什么在此处才可得（如「缺省保存路径为什么在闭包返回后才分配而显式路径提前校验」）。考的是对依赖链的理解。
4. 架构事实题——装配关系、调用链、宿主分型（如「浏览器宿主的出站调用走哪条通道」）。考对全局的把握。

避开的题型：字面事实题（「这个常量是多少」——能 grep 到的问它无意义）；主观意图题（「作者当时怎么想的」——作者自己都可能答错）；未来假设题（「如果要支持 X 怎么改」——没有唯一答案）。

## 出题规范：近似变体

选项设计是本模式的核心技艺，目标是让每道题都真正考验理解：

- 全部选项由近似变体构成：每个选项都是「看似都对」的合理陈述，差异在因果链的细微处（根因 vs 表层结果、主因 vs 次因、事实 vs 推断），禁止明显错误项充当干扰
- 四选项覆盖同一问题的不同归因深度：如「看依赖的资源类型 / 看功能闭环内聚 / 只是目录整洁 / 说不好」——前三个都有表面合理性，但只有一个经得起代码核实
- 题面指向动机与根因（「为什么 X」「Y 触发时会发生什么」），不问字面事实
- 每批 ≤4 题，一次 AskUserQuestion 问完；题量以考点清单的核心考点为限（3-9 题），不凑数
- 可在选项 description 里埋入部分正确 + 部分遗漏的复合表述，考「能否区分完整因果链与半截因果链」

## 校准纪律

答案回收后逐题对照代码事实校准，标准：

- 答对：给确认，并在确认中把用户答案隐含的因果链展开说全（用户的「对」可能只是直觉对）
- 答错：给代码级反证——引用 `file:line` 与关键行为描述，不用「你错了」这类裸断言
- 方向对但浅：指出遗漏的根因层（如「你抓住了表层（ext 自动推导），但漏了信息可用时机这个根因」）
- 引用注释或文档作反证前，先核实该注释未漂移（本模式选题阶段已做反向核实，校准阶段直接引用核实结论）；发现新漂移记入真实问题清单
- 用户断言与代码/文档事实矛盾时（如「双宿主已经没了」vs 注释与报告都说有）：不下裁决，先自己反向核实（grep 调用方、读装配点），核实后用证据说话——用户的直觉可能是对的，但须让它站上证据链
- 用户抱怨出题方式而非面对答案时，如实指出该模式（用环境归因替代自我归因），但不纠缠，继续流程

## Insight 沉淀

每批校准后穿插 insight 块，2-3 条，写本次考点特有的可迁移认知：

- 好的 insight：本仓库的统一契约（「失败软降级为 error 文案回喂模型，模型是错误第一处理者」）、本变更特有的设计模式（「枚举来自注入而非硬编码——加能力只加闭包」）、方法层面的教训（「注释可信度取决于它距架构变更的时间距离，反向 grep 调用方是戳破漂移的手段」）
- 坏的 insight：泛泛编程常识（「先校验再调用省成本」「串行避免竞态」）——任何语言任何仓库都成立的话不值得写

## 批评尺度

用户答错、答案暴露「写了但没理解」、或断言证据不足时，直接指出：

- 批评基于已确认的事实链（某题答错 + 该题对应代码里有明确行为），不基于推测
- 可以点出行为模式（如「测试通过 ≠ 你知道为什么」「用环境问题替代自我归因」），但一句话点到即止，不做心理分析
- 用户答对或有合理直觉时必须如实给分——严厉是纪律不是人设，不虚捧也不为批评而批评

## 收尾报告结构

1. 逐题对错清单：题号 / 考点类型 / 对错 / 一句话校准结论
2. 理解缺口汇总：暴露了哪些「写了但没理解」或「记错了行为」的点，按重要性排序
3. 真实问题清单（如有）：考校过程中发现的注释漂移、僵尸分支、文档过时等，逐条给处置建议（清理 / 修复 / 忽略理由），留给用户决策
4. 下一步建议：接 flow-mem 沉淀本次认知、或接 flow-dev 处置真实问题清单
