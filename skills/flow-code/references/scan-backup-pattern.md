# --scan 坏味道扫描规则：backup/兜底模式

> 来源：2026-07-28 某内部项目全仓排查 + 双模型正交审查修正 + 10 项清理实证。
> 本文是 Workflow B 的规则全集：坏味道分类、搜索模式、判定框架、输出规范、判定纪律。

## 什么是 backup 模式

AI 堆功能时的典型倾向：写了实现 A，又怕 A 坏掉，于是补一个 B 兜底。单看每一处都像稳健工程，合起来是系统性坏味道——默认值方向错误让门禁失效、失败被伪装成正常空结果、备份路径不可达或与主路径同义。扫描的目标是把这类模式从「设计内降级」（文档化特性，豁免）中分离出来。

## 判定框架（每个命中过三问）

1. 默认方向：失败时落到更宽还是更严？更宽 = fail-open（门禁失效类，最危险）；更严 = fail-closed（多一次确认/少跑一次，通常可接受）。
2. 可观测：降级/丢弃/兜底发生时有 warn、计数或显式标记吗？没有 = fail-deceptive（上层无法区分「真没数据」与「系统坏了」）。
3. 可达：备份路径真的可达吗？不可达 = 死代码直接删；可达但与主路径同义 = 冗余收敛；可达且守护唯一失败模式 = 设计内降级，豁免。

三问的答案组合决定进哪个分轴（见输出规范），不判定不进列表。

## 坏味道分类与搜索模式

### 1. 默认值方向错（fail-open）

信号：normalize/parse 函数把非法、空、未知输入归到更宽松的默认值。
判定：默认值权限更低、门禁更松即确认。修法是反向默认（最严档 + warn），不是删除。

```
rg -n "\?\? '?L[0-9]'|default.*=|非法|空值" —— 聚焦归一化/映射函数
```

### 2. fail-deceptive（失败伪装成空结果）

信号：catch 后返回空数组/空串/空对象，无日志无标记。
判定：消费方拿到空结果后无法区分「无数据」与「故障」即确认。修法是显式降级标记（如 degraded 字段）、500 上抛或 warn，不是一律抛错。

```
rg -n "catch" -A 4 | rg "return (\[\]|''|\{\})"
```

### 3. mock 降级无环境门控

信号：缺 key/配置时返回 mock 假数据，开发与生产同行为。
判定：生产环境也会走 mock 分支即确认。修法是环境门控（production 显式失败，非 production 保留 mock 开发惯例），不是删 mock。

```
rg -n "mock" server/ packages/ | rg -v "NODE_ENV|allowMock|import.meta.vitest|spec|test"
```

### 4. 双路径备份（A+B 同职）

信号：try{A}catch{B} 或 if/else 两条路径做同一件事。
判定：逐条确认可达性与语义差异。B 只是 A 失败后的同义重试（如 try{map(parse)}catch{filter(safeParse)}）→ 收敛为单遍；A 在数据干净时是 happy path 不算死代码，但结构仍冗余。注意别把 happy path 误报成死代码（正交审查实测纠过的错）。

### 5. 幻影定时器 / race 输家副作用

信号：Promise.race 的兜底 setTimeout 回调里写日志/告警/状态。
判定：race 分出胜负后输家定时器仍到点触发，回调副作用幽灵执行。修法：回调只做无副作用 resolve（可 Symbol sentinel 区分超时），胜负判定后 finally clearTimeout。

```
rg -n "setTimeout|setInterval" -A 6 | rg "console\.(warn|error|log)"
```

### 6. 内存双写（假持久化）

信号：同一状态写两处（文件+内存变量、Redis+Map），读时按优先级回退。
判定：写主存储失败后读内存副本，表现为「持久化成功」但重启即丢。修法：单源化，写失败留 warn 可观测。

```
rg -n "^let memory|memoryLast|内存降级|内存副本" 
```

### 7. 过期备份物入库

信号：.bak/ 目录、_old 后缀、backup 命名文件、整块注释掉的旧实现。
判定：git 跟踪的备份物先 diff 核对与现行版本异同（防止误删唯一版本），确认零引用后删除。

```
rg --files | rg "\.bak|_old|backup|备份"
```

### 8. 保留参数 + lint 压制

信号：签名保留下划线前缀死参数，靠 eslint-disable 压 unused-vars。
判定：参数自某次重构后从未被消费即确认。修法：签名收敛 + 调用方同步清理，disable 注释一并删。

```
rg -n "eslint-disable.*no-unused-vars" -B 3
```

### 9. 双端兜底重复

信号：同一 fallback 逻辑（如 name ?? id）前端后端各一份。
判定：违反类型绑定原则（前端不重映射），收敛到 server 单点；链路验证：前端空值 → API 落 NULL → server 读取侧回填，展示行为不变。

### 10. 多层防御重叠

信号：多层机制守护同一事件（事件监听 + 轮询 + 超时）。
判定：枚举每层守护的失败模式，各自唯一 → 保留并注释标注失败模式（不是 bug，不收敛）；有重叠 → 收敛。这是最考判定的一类，误伤设计内防御比漏报代价大。

## 输出规范：分轴列表

按两轴四区输出，排序即处理优先级：

- 轴一 运行时风险：能命名具体 failure_scenario（什么输入/状态 → 什么错误结果）；修复需附测试
- 轴二 代码卫生：零运行时风险的冗余/死代码/重复；纯删除/简化
- 豁免区：设计内降级、文档化特性、每层守护唯一失败模式；不动，列出让读者知情
- 知晓区：轻度防御性，风险极低；不动

列表项格式：文件:行号 — 模式名 — 一句话问题 — failure_scenario。找不到 failure_scenario 的命中不许进轴一。

## 判定纪律（正交审查实测纠过的四类错）

1. 必然与概率分开：多实例并发问题要写清是「必然重复执行」还是「TOCTOU 概率窗口」，并评估既有护栏（如 DB 状态检查）兜住了多少——定性过重会导致修复优先级错排。
2. happy path 与死代码分开：主路径在数据干净时正常运行就不是死代码，只能说结构冗余。
3. 覆盖完整先于深度：扫描第一步先铺面（fd/rg 列出全部目标目录），漏掉某整个目录是漏检主因——实测漏掉 packages/orchestration-agent 导致两个最高危发现险些缺席。
4. 重要清单接正交审查：定性结论（尤其 fail-open 定性、必然性定性）建议接异模型审查（外部审查 runner 或全新上下文子代理）修正后再作为清理依据。
