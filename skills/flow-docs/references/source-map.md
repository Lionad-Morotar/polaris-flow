# 源码映射深化执行手册

由 SKILL.md Workflow C Step 1–2 调起。定义变量抽取、大纲解析、单页深化撰写契约、源码锚点格式与锚点验证协议（机械越界校验 + 编辑器视觉抽查，后者复用 flow-tour 的编辑器跳转实现）。

## 变量

- 大纲文件（来源：用户输入；默认：无（必需））：含文档站点目录结构的 Markdown（如 `site-directory.md`）
- 已有报告（来源：用户输入 / 输出目录扫描；默认：无）：已完成的参考报告，用于对齐深度、语气与格式基准
- 输出目录（来源：用户输入；默认：`docs/.report/`）：命名 `<num>-<name>.md`
- 源码根目录（来源：用户输入 / 仓库结构推断；默认：无）：项目主源码目录（`rust/`、`src/`、`packages/` 等）
- 核心模块（来源：用户输入；默认：无（必需））：重点调研的 crate / package / 子目录名称列表

## 大纲解析

读大纲文件，提取所有待撰写页面的标题与顺序编号；按 `<num>-<name>` 命名匹配跳过已有报告的页面，输出页面任务列表。用户可指定只处理某区间或某几页；无指定则按序全部处理。

## 单页深化契约

每页由主代理 inline 执行，**不设撰写/审校角色分工**——审校的机械部分由脚本承担（见「锚点验证协议」），认知部分由撰写者自检承担（见「撰写者自检清单」）。单页源码调研面大时，可派 3~4 个研究子代理（`subagent_type: "Explore"`）各负责一个核心模块，返回关键函数、调用链、配置文件等发现；子代理是调研扇出的实现细节，不是角色分工。需要结构化共写时可选调 `doc-coauthoring` 技能。

**撰写要求**：

- **必须是单个文件**：`docs/.report/<num>-<name>.md`，严禁拆分为多个章节文件。
- **严格基于原文 ToC 深化**：标题与 `##` 必须与原文档一致；为每个主要章节增加 `###` 子节解释对应源码实现细节，不要重新组织成新的文章结构。

**源码锚点格式**：

- 所有源码链接指向仓库内文件，使用仓库根目录的绝对路径形式（禁止相对路径如 `../src/`）：

```
[file.ext](/<source-root>/<module>/path/to/file.ext#LXX-LYY)
```

- 行号锚点 `#LXX-LYY` 必须精确，确保点击后直接跳转到对应代码位置；单行引用写 `#LXX`。
- **填充即验证**：填每个锚点前，先用编辑器打开对应行确认是目标代码（见「编辑器视觉抽查」），再落笔写数字。禁止凭记忆或搜索结果片段猜行号——搜索结果的行号是搜索工具上下文里的，未必是仓库文件的实际行号。

## 锚点验证协议

每篇报告写完后必须过两层验证，缺一不可。

### 机械越界校验：verify-anchors.mjs

```
node ~/.claude/skills/flow-docs/scripts/verify-anchors.mjs docs/.report/<num>-<name>.md
```

批量解析报告中全部 `#LXX-LYY` 锚点，校验三件事：目标文件存在（`/` 开头按 git root 解析，否则按报告所在目录）、行号不越界（≤ 文件总行数）、起始行 ≤ 结束行。`http(s)://` 外链自动跳过。

输出 JSON 汇总（`total` / `passed` / `failures`，failures 含锚点在报告中的行号与失败原因）；任一失败退出码 1。**失败零容忍**：按 failures 逐条修正后重跑，直到全绿——不交付含越界锚点的报告。传目录则递归校验其中全部 `*.md`，适合整批大纲收尾时一次总验。

### 编辑器视觉抽查

机械校验只证明「行号存在」，不证明「该行是目标代码」。以下场景须打开编辑器肉眼确认：

- **填充锚点时**（填充即验证，主要场景）；
- 机械校验全绿后，抽查 4 个以上关键锚点（函数入口、调用链关键节点、配置定义）；
- 正文引用的代码串与锚点附近实际代码不一致时。

**CLI 形态**：flow-tour「代码位置跳转」是浏览器侧实现（自定义协议 + 隐藏 iframe 触发，机制见 `~/.claude/skills/flow-tour/references/website.md`「代码位置跳转」章节，协议表见 `~/.claude/skills/flow-tour/templates/editor.ts.template`）；代理执行场景用 CLI 侧等价能力，编辑器优先序与 flow-tour 保持一致（Insiders → Cursor → Windsurf → VS Code）：

```
code-insiders -g <绝对路径>:<行号>   # 本机默认
code -g <绝对路径>:<行号>
cursor -g <绝对路径>:<行号>
windsurf -g <绝对路径>:<行号>
```

`-g` / `--goto` 是 VS Code 系 CLI 共用参数，打开文件并定位到指定行。preflight 会探测可用 CLI；全部缺失（仅告警不阻断）时降级为 `sed -n '<start>,<end>p' <file>` 文本抽查，但不要跳过抽查本身。

## 撰写者自检清单

每篇报告交付前逐项过一遍（认知类验证无法脚本化，由撰写者自己承担）：

1. **技术准确性**：每个技术描述与源码事实一致；函数调用链、职责归属、配置/文件名等容易误植的细节，逐一对照调研发现复核。
2. **锚点可验证性**：全部源码链接已过 `verify-anchors.mjs` 且关键锚点已视觉抽查。
3. **单文件完整性**：未产生多余的 `.md` 拆分文件。
4. **源码字符串一致性**：正文引用的代码片段与实际源码一致（`rg` / `sed` 抽查 ≥4 处）；不一致时先判断是版本漂移还是引用错误，再决定改引用还是在正文标注漂移。
5. **质量基准对齐**：存在已有报告时，深度、语气、格式与其一致。

## 边界情况

- **无已有报告**：以首篇完成报告为基准，其后页面对齐它；首篇撰写时主动与用户确认深度预期。
- **锚点指向仓库外文件**（构建产物、外部依赖）：此类锚点不应存在——源码映射只针对本仓库文件；确需引用外部代码时正文 plain text 描述，不用链接锚点形态。
- **同一文件锚点过密**（10 行内多个锚点）：考虑合并为一个区间锚点，减少行号漂移噪音。
- **大纲页面与源码模块不对应**（文档讲的是概念，代码里没有同名模块）：在 `###` 子节中说明概念到实现的映射关系，而不是硬造锚点。
