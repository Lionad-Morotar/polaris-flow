# 提交信息规范（commit message）

提交信息的单一事实源。本技能各模式与其他 flow 技能（flow-dev / flow-release / flow-dx / flow-distill 等）需要写 commit message 时引用本文件，不再各自维护规则。

message 的读者不只是提交者自己：周会回顾、迭代报告、自动化摘要工具都以 message 为原始素材，且通常只做少量改写甚至直接引用原文。写得含糊，呈现就会被二手改写稀释；写得成稿化，呈现就忠实。

分两层：**切片层**（每条 commit 怎么写）与**叙事层**（merge / release 怎么写）。

## 切片层：单条 commit message

* 格式：`<type>: <高度凝练的 spec>`；多行 spec 用空行 + `- ` 列表展开
* type 以 commitlint type-enum 为强制执行口径（见 `init-hooks.md`，含 `feat`/`fix`/`refactor`/`docs`/`style`/`test`/`chore`/`perf`/`build`/`ci`/`revert`/`wip`/`release`/`merge` 等），本文件不另维护清单防双真源漂移；带 scope 写作 `<type>(<scope>):`，scope 取模块/域名（如 `chat`、`db`、`assets`）。优先级仲裁：**项目既有 `git log` 惯例 > 本文件默认词汇**
* 垂直切片：每个 commit 可独立运行、可独立测试；按修改意图聚类，不按文件类型聚类
* 标题不描述测试状态（「通过」「全绿」等）；但 xfail、flaky、跳过的套件属于必须告知读者的现实约束，写进 body（见「body 与 footer」节），不是消失
* 禁夹带自造流程记号（切片序号、Step、审查轮次）——读者无法解析的记号会被略过，所在提交随之隐形；可跳转的 issue/PR 引用（`Closes #123`）不受此禁，且建议放 footer
* 措辞按可被直接引用的成稿标准写：主谓宾完整、结果导向。对比：`fix(report): 修复导出时序问题`（读者需自行脑补细节）vs `fix(report): 导出结果按提交时序分段渲染，历史回放可完整还原`（可直接引用）
* 大变更（可操作口径：净变更 >300 行，或涉及 ≥5 个模块）给出真实规模指标（覆盖列数/模块数/切片数），规模是读者判断权重的直接依据；**清理与重构写明删除量**——`refactor(theme): 铲除浅色 token 资产（-2.3k 行）`，否则删除类工作在历史中零存在感
* type/scope 词汇保持稳定——它们是历史归类与统计的信号轴，漂移会把同一项工作拆散到多个类目下
* 单条切片不承载「主题——要点」双段结构——双段结构是叙事层摘要行的专属形态（见下），切片承载它会模糊修改意图边界；但尽量不使用破折号，我不喜欢。

## body 与 footer（why 层）

标题回答 what，body 回答 why——这是 commit 里最值钱、也最容易被省略的部分。没有 why 层的历史会很整齐，但很浅：读者能复述你做了什么，无法理解为什么这么做、为什么不能那么做。

* body 按需写，内容候选：隐含假设与约束、被否掉的替代方案及否决理由、已知不稳健之处、xfail/flaky/跳过套件等测试现实
* 明显的单点修改（一行 fix、 typo）不需要 body——why 从 diff 自明的，写了是噪声
* footer 承载结构化引用：`BREAKING CHANGE: <影响面与迁移指引>`、issue/PR 引用（`Closes #123`、`Refs #456`）；破坏性变更必须在 footer 显式声明，不埋在标题或 body 里

## 叙事层：merge / release message（章节索引）

历史消费者（周会回顾、审查 Agent、未来的自己）按 **merge 与 release 提交**当章节索引读历史，直提是盲区——直提占绝对多数的仓库，读者只会逐条放弃。垂直切片保留在分支内，主干上要有叙事：

* 单点修改（一两个 fix/feat）直提即可；**一簇同主题工作（≥5 个切片）走分支 + merge --no-ff**，merge message 格式：

  ```
  merge(<scope>): <主题>——<要点1/要点2/要点3>
  ```

  （摘要行是规范内唯一刻意的「主题——要点」双段结构；切片层禁用该结构，见上）

  merge 主题按「可直接进入迭代报告」的标题标准写——它就是报告章节名的来源；分支内允许试错与回退，merge message 描述收敛后的最终形态，不罗列中间态

* **批量同质提交必须走分支**（如素材/种子批量入库，几十上百条同句式 commit），一条 merge 汇总：`merge(assets): 图标库二期 120 枚入库——导航 24/操作 56/状态 40`；直提同句式刷榜会让读者认定直提不值得读
* **sync merge 合并他人或并行流内容时注明归属**：`merge: 合入 <模块> 改造（<作者>）`——按 author 字段统计的口径下，裹挟不点名会让被合并方的工作归到合并发起方名下
* **release commit message 带本版批次清单**（多行 body，一行一条，直接摘录本次 Changelog 版本段条目，按重要性降序——摘要读者倾向保留头部条目），它是读者切窗口的边界，裸 `release: vX.Y.Z` 等于空白章节页：

  ```
  release: v0.8.0-alpha.2

  - 报表导出支持 CSV 与 PDF
  - 通知中心未读徽标与免打扰时段
  - 深色模式对比度修复
  ```
