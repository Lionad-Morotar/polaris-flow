# 一致性审查手册

> 定位：技能族一致性审查的执行手册——审查单个技能内部及技能之间的契约、措辞与结构一致性。
> 来源：flow 技能族七轮试审（覆盖审查流、元技能、cron 状态机、路由包装、站点库、教学双分支、大状态机七种类型）的经验固化，全部结论经 file:line 证据与命令核实。
> 读取时机：批量审查技能时通读；单技能大修后自查时按维度回查。

## 核心关切

极端语气不可怕，可怕的是描述带歧义——一句话有两种可执行解释，且两种解释导致不同的 agent 行为。语气强弱本身不是问题，歧义才是。

## 严重度分级

- S1 行为分叉：能构造出「agent 按解读 A 做 X、按解读 B 做 Y、X≠Y」的场景；或契约已字面分叉。
- S2 需推理：agent 大概率猜对但需要跨文件综合；判据缺失；措辞系统性误导。
- S3 会发散：当前一致，但结构注定未来分叉（双头、化石、纪律无执法者）。

## 八维 rubric

### 1. 逻辑自洽

- 跨文件矛盾：同一技能两处文件对同一事做不同断言。高发于「主文 + references」与「SKILL.md + 脚本输出」。
- 死分支 / 缺失 fallback：错误路径声明了「告警不阻断」，workflow 却没有告警后的分支（如外部 CLI 缺失 + 依赖该 CLI 的 target 类型）。
- 未定义变量与同概念异措辞。
- 子项 分支闭环：决策树的每个分支在 workflow 都有执行者；checklist / 验收项的每个动作在 workflow 都有执行步骤。验收项在 workflow 找不到执行步骤时，几乎总是流程漏接而非清单多写——checklist 是 workflow 缺步的告密者，用验收项反查 workflow 比顺读高效。
- 子项 状态完整性：state schema 的每个字段都要有 consumer；声明、存储、甚至终端展示过但全链路无人消费的字段是幻影状态（典型：预算字段无超限动作、失败计数无阈值动作、phase 枚举齐全但零写点）。每个参数都要有执行路径：定义在 argument-hint 却无 workflow 路由的参数同病。
- 子项 生产/消费载体匹配：consumer 存在但载体错位——producer 写文件、consumer 读 state 数组，两边互不相见。这是幻影状态的进化型，查法从「字段有无 consumer」升级为「两侧载体是否一致（文件 / state / 终端）」。
- 识别信号：「声明了、存下了、展示了，然后没有人据此做任何事」。

### 2. 歧义

- 定义：不是「不够细」，而是「可以这样做，也可以那样做，且结果不同」。
- 子项 例外异地化：绝对禁令的例外散布在其他文件，禁令现场只枚举了部分例外——只读一侧的 agent 拿到相反指令。禁令与反例指令异地存放时，只读一侧必然得到相反行为；例外条款必须与其主条款同段共处，异地引用只能指向例外清单本身，不能把例外拆散。
- 子项 标注不对称：同层部分章节带模式 / 范围标注，未标注项被读者推断为「全体共享」；若模板 / 脚本再用对比性注释强化（A 字段注了「某模式可忽略」、B 字段没注 → B 被推断为必填），推断固化成错误契约。部分标注比不标注更糟——部分标注训练了「无标注 = 共享」的推断。要求：同层章节要么全标注，要么全不标注。
- 子项 假等式括注：括注同位语把两个不等价的概念等同起来，括注极易被略读而主句断言过宽。
- 子项 隐藏前提碰撞：每句话单独看都真，合起来描述了一个不可能态。行级审查看不出来，必须先对运行时建模才能发现（如「触发器仅在上游空闲时 firing」与「上一轮仍在跑」并存）。
- 子项 残留措辞与化石结构：历史设计的遗留，当前指代对象已不存在——轻则一句失去参照的话（多投票时代的「单票即携带」、无逻辑关联的状语），重则整个文件结构（被合并的旧技能留下的 frontmatter）。
- 识别信号：给出两种解读，检验是否都能从文本找到支撑且行为不同。

### 3. 语气-约束力匹配

前提：极端措辞靶子清晰即为正面样本（「不许虚构」「永不覆盖」式红线）。要查的是语气与约束力的错配，四个子模式：

- a 靶子不明：强语气指向一个全文没有先行词的概念。
- b 笃定包裹含糊：措辞断言式、操作却含混，agent 因语气确信把含混当精确，自行脑补一种实现（如笃定地写一个与主句互斥的合并策略名）。
- c 弱语气弱化核心：核心路由步骤或硬约束用了「也许」「建议」——硬约束在别处有 throw / 报错佐证时，唯一弱语气处就是误导源。
- d 章节稀释：红线级约束混入「提示 / 其他」节，与琐碎事项并列，且技能没有独立红线节。
- 识别信号：对每个强句问「只读这一句的 agent 能做对吗」；对每个弱句问「不照做会出什么问题」。

### 4. 双头治理

- 分级：壳摘要 + refs 细则是低危双头（摘要容忍漂移）；壳完整 + refs 完整是高危双写（两处都可独立执行，分叉只是时间问题）。
- 实证规律一：有意双写也会分叉——声明了「两文件同步维护」的双写仍在月内字面分叉（事件名差一个前缀级别）。靠记忆维护同步是已证伪的实践。
- 实证规律二：例外条款优先分叉。主句识别度高，例外条款是括注 / 尾句，抄写时最先被丢——红线双写丢的永远是例外分句。这从句法位置解释了为什么红线双写高危。
- 修法：不是「仔细抄」，而是单源 + 引用；若双写刻意保留，必须声明层级关系与同步程序（正面范式见「正面模式」节）。

### 5. 触发路由一致

- argument-hint ↔ 参数节 ↔ workflow 分支三方对齐。
- 模式与 flag 的边界：哪些是模式（互斥、参与路由）、哪些是 flag（附着于某模式）必须写明；「其他 --* 报错」式兜底会把合法 flag 也兜进去。
- 多维调度串行化：参数维（flag 路由）与状态维（phase 门控）应串行两层；入口分流只看调用来源、门控只看状态时，flag 参数掉进两维之间的缝隙（如恢复参数被状态门控的 no-op 吞掉）。

### 6. 模板与实况一致

- 模板默认值 vs 仓库实况：模板写进 frontmatter 的默认值，要与技能族的实测分布核对（曾出现模板默认开启某声明、实测家族 minority 才开启、最大技能反而不开）。
- 模板幻影契约：模板缺某个字段，主文逻辑却依赖它——「默认值」让行为偶然正确，契约本身是缺的。
- 纪律声明者 ≠ 纪律执法者：纪律写在 checklist 而执法工具（lint 规则表）不覆盖，家族自己最先破（薄壳行数纪律无 lint 规则，两个大技能先后超标）。无执法者的纪律比没有纪律更糟——它制造「我们守纪律」的幻觉。修法二选一：补执法规则，或删掉这条纪律。
- 识别信号：凡模板 / 纪律性断言，逐条拿仓库实况实测对拍，不靠阅读。

### 7. 运行时模型一致性

- 顺序：先对触发机制建模（cron / hook / worktree 清理 / 子代理的运行时语义），再读措辞。
- 措辞与触发语义相容性：技能描述的状态要与触发机制的实际 firing 条件相容（隐藏前提碰撞是本维度的静态表现）。
- 工具语义边界与领域词多义：workflow 动作与红线的交叉验证中，红线名词要代入工具的真实语义——领域术语在不同作者笔下各取一义（「未跟踪」既指用户未提交代码，也指被 git exclude 的产物；清理 worktree 的工具对未跟踪文件要求显式确认参数），两侧各取一义时 workflow 会指挥一个被自己红线条款禁止的动作。
- 虚假安抚：局部安全声明不注明边界会被泛化（「清理不删除运行态状态」为真，读者推广为「清理整体安全」，而工作区内的产物恰不在声明范围）。「X 安全」式声明必须同时说明 Y 不安全。

### 8. 分布边界一致

- git 跟踪集 × SKILL.md 索引链接集求差集：链了但不在 git = 外部安装者死链；在 git 但没链 = 孤儿文件。
- 目录也是数据：索引表暴露未发布文件的路径、用途、技术摘要——隐私设计保护了正文而漏了索引时，索引就是泄漏面。公开发布的壳里，对未发布内容的枚举要脱敏或移除。
- 验证器上下文依赖：lint 结论可能依赖在哪台机器上跑——本地存在而被 gitignore 的文件让断链规则静默，fresh checkout 上同一技能告警爆表。「提交前零告警」可能是开发环境幻觉。
- 跨技能契约：参数语义级契约可人工对拍核实（如透传参数的默认值断言与下游技能实测一致——正面）；文件路径级依赖（直接调下游技能的脚本路径）若无自检则是裸依赖，下游改名即断裂。依赖清单要覆盖 preflight 实际 spawn 的每个下游。

## 机械检查清单

不依赖阅读理解的程序化操作，按投入产出比排序。前五项都是一次操作抓多类问题的高杠杆项。

1. `git ls-files <skill>` × SKILL.md 链接集求差集——一次抓死链 + 孤儿 + 索引越界泄漏。
2. state schema 每个字段 × 全 workflow 读写点配对——抓幻影状态与幻影 phase。
3. 每个参数 × workflow 路由配对——抓幻影参数与模式 / flag 混淆。
4. 每条绝对禁令句（严禁 / 禁止 / 一律 / 永不 / 不得）× 同段例外枚举——抓例外异地化。
5. 同一规则的多处定义逐字 diff，重点看例外条款在各处是否都在——抓双写分叉。
6. 脚本输出 schema 每个字段 × 文档消费点——抓未兑现的设计意图（字段为消除歧义而生、文档没接上线时，文档层必有对应歧义）。
7. 标注对称性：同层章节部分有模式 / 范围标注 → 要求全部标注。
8. workflow 动作 × 红线条款笛卡尔积，红线名词代入工具真实语义——抓红线自攻击与领域词多义。
9. 分支覆盖矩阵：决策树分支 × workflow 步骤；验收项 × workflow 步骤——抓漏接分支与无主动作。
10. 纪律断言 × 执法工具规则表——抓无执法者的纪律。

## 正面模式

审查不只是找错。以下范式经试审验证，值得作为其他技能的对照基准：

- 声明层级的双头：人类可读视图自报「本文件是脚本的人类视图，精确集以脚本为准，模型上下线先改脚本跑通测试再同步本文件」——双头被声明了层级和同步程序就可以接受。
- 给绝对规则加例外的五要素：软性判据 + 标题括注 + 自解歧括注 + schema 枚举值 + CHANGELOG 记录。
- 例外聚集：复杂规则集中定义一次，各执行步骤只引用（如停止序列集中定义、各 Step 写「执行停止序列」）。
- 询问白名单：显式枚举「仅这几类必须询问用户」，其余自决——比「不要暂停」单禁令更可执行，因为它回答了「什么时候该暂停」。
- 自觉元纪律：作者预见到 agent 会犯的错误模式并显式封杀（「禁止在脑中按散文推断路由，一律走脚本」）。
- 模板-文档零分叉：可执行断言由脚本 / 模板实现，模板引用与实际文件 diff 为零——文档说谎的空间被工具消除。
- 单一真相源委托：检测逻辑 spawn 下游技能的 preflight 并注释点明委托关系，避免检测逻辑双头。
- 自解歧括注：强语气后原地划界（「并非不做计划！而是先计划再自动确认」），是强语气与清晰度兼得的范本。

## 边界：不算问题

- 极端措辞本身，靶子清晰即可。
- 中英混排、英文祈使句的角度 / 规则文本（继承上游风格的刻意选择）。
- 冗余强调：两处复述同一规则但措辞未分叉，只记 S3 双头风险，不记 S1。
- 壳摘要 + refs 细则的低危双头，摘要容忍漂移。
- 自解歧括注不是冗余，是正面信号。

## 审查顺序

1. 先建模运行时（触发机制、工具语义），再读措辞——隐藏前提碰撞只能这样发现。
2. 用验收项 / checklist 反查 workflow，不要只顺读 workflow。
3. 发现幻影字段时做法医式溯源：反查脚本作者为什么留这个字段——未兑现的设计意图往往直接给出文档层歧义的修法。
4. 差集法先于阅读法：机械检查清单的前五项跑完，再逐段读。
5. 每轮审查记录新出现的模式并回灌 rubric——rubric 本身是被审查进化的对象，七轮试审中它从 5 维长到 8 维，每一维都要求有跨技能复现证据才转正。
