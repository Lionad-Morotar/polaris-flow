# 需求树拆解（Dissection）—— 把原始想法递归拆解为可证伪的叶需求

`--dissection` 打开时，Step 1 UltraThoughts 在实现侧分析之后追加需求树拆解。需求树回答"要做什么"的穷尽性，产物落档到独立拆解文档（`docs/dissections/<task-slug>.md`），不并入 UltraThoughts 文档；下游 DevGoal Slice 回答"按什么顺序做"。需求树是 grill-me 自答与 Slice 划分的原料，不替代它们。

## 拆解规则

- **数量从需求推导，不设上限。** 节点数量是推导出来的，不是选出来的：3 个叶节点合适就 3 个，30 个合适就 30 个。为了凑数而合并会掩盖依赖与盲区；为了显得详尽而硬拆会制造伪需求。
- **递归拆解，直到每个叶节点通过两条终止测试：**
  1. **可独立验证** —— 能明确指出"用什么实验 / 截图 / 测试 / 数据证伪这条需求"，且无需等待其他节点完成。沿用目标定义性属性的 Verification / Confidence 语义。
  2. **原子性** —— 一个节点只陈述一件事。无法用 ≤5 个词命名且不含"和"，说明塞了两件事，继续拆。
- 如果发现自己在控制节点总数，方向就错了 —— 让数量从需求内容自然长出。

## 节点字段

每个节点（中间节点与叶节点）必须包含：

- **编号**（`R1`、`R1.2` 形式，体现树结构）
- **名称**（≤5 词，动作或对象优先，不含"和"）
- **Why**（1 句话，存在的理由；隐含假设在此显式化）
- **验收标准**（叶节点必填，3–8 条；中间节点省略，由子节点并集继承）
- **依赖**（显式节点编号，如 `依赖 R1.2`；无依赖写 `none`。需求间弱依赖 —— 如数据模型阻塞接口、安全网阻塞迁移 —— 为下游 Slice 排序提供输入）

## 验收标准试金石

叶节点的每条验收标准应当：

- **可观察** —— "构建成功" 可以；"感觉对了" 不行
- **原子性** —— 每条标准一个事实
- **可证伪** —— 能回答是 / 否，不是"差不多"
- **与命令或证据绑定** —— `pnpm test` 输出、文件存在性、截图对比、基准数据

差："搜索功能好用。"

好：

- `pnpm vitest run tests/search/` 通过
- 输入空字符串返回全部结果且不抛错
- 输入 200 字符时响应 < 500ms 且不截断报错

## 拆解形态参考

形态是检查清单而非模板 —— 任务不需要的分支剪掉，任务特有的分支补上。

### 功能开发形

根需求 → 数据模型 / 核心行为（黄金路径）/ 表面集成（路由、导航、鉴权）/ 状态与边界（空、加载、错误、未授权）/ 打磨加固（文案、a11y、性能、安全）

### 存量重构形

根需求 → 安全网（覆盖率不足先补特征测试）/ 提取（不改变行为）/ 迁移（逐个调用方）/ 删除旧代码 / 回归扫描

### UI 工作形

根需求 → 令牌与原子（匹配现有设计令牌，不重新发明）/ 布局（响应式网格）/ 内容表面（按重要性排序）/ 交互（动画、状态过渡）/ 状态（空态、加载态、错误态 —— 占打磨工作的大头）

### Bug 修复形

根需求 → 根因（非症状）/ 复现用例由红转绿 / 同模式排查（是否多处需修）/ 回归面（还有哪些代码路径使用这段代码）

## 自我批评三问（拆解后必跑，就地重写）

1. **可证伪性** —— 每个叶节点的每条验收标准都是是 / 否测试吗？标记任何说 "works"、"good"、"合理" 而没有可衡量谓词的描述，就地重写为与命令或证据绑定的形式。
2. **原子性** —— 是否有节点把两件事打包成一件（名称含"和"、验收标准分属两个不共享验证的事实）？拆开。
3. **覆盖完备性** —— 叶节点并集是否等于原始想法的全部实质，不多不少？每个父节点是否等于其子节点并集？漏的补上；溢出的不删，显式标记为超出范围（防止隐性 scope creep）。

三问必须产出发现或 `clean` 裁决，并记录在拆解文档末尾。在真实需求上永远静默 `clean` 是戏剧，不是纪律。

## 外部正交审查（落档后必跑，一轮 Gate）

拆解文档落档后、进入下游（grill-me / DevGoal）之前，由外部审查 runner 对拆解文档做一次外部正交审查。自我批评三问是生产者视角的自检，与拆解共享同一套隐含假设，查不出自己假设里的盲区；拆解又是下游 grill-me 问题清单与 DevGoal Slice 划分的原料，原料失真则下游全盘失真，因此必须引入外部视角复核。

- **触发**：`--dissection` 开启即触发，与流程模式（`--mode`）无关，且恒执行——不适用 Step 6 code-review 检查点「默认跳过、较大改动才触发」的规则；`--dissection` 本身就是显式的拆解请求，拆解一旦发生即须过审；`--skip-review` 跳过并在 `reviews[]` 记录 `status=skipped`。
- **Prompt 用陈述式**：陈述需求树的规模与覆盖边界（中间节点数、叶节点数、自我批评三问的裁决结果），不下达"重点关注 X"的审查指令，不主动暴露自评盲区——指令式 prompt 会把审查模型的注意力框进主代理的视角，复现同一盲区。
- **Gate 裁决（一轮，不循环再审）**：逐条裁决审查发现——
  - **接受** → 就地重写拆解文档对应节点（名称 / Why / 验收标准 / 依赖），波及父子关系时同步调整树结构，并重跑受影响节点的终止测试；
  - **驳回** → 决策台账记录驳回理由与代码库证据。
- **裁决留痕**：裁决摘要（审查模型、发现条数、接受 / 驳回分布）追加到拆解文档末尾，与自我批评三问的裁决记录并列。
- **审查失败不放行**：runner 未返回 JSON 或全部审查模型 `failed` / `degraded` 时，记录 `external-review-failed` blocker，phase → `blocked`，禁止进入 Step 2——拆解结果未经正交检查不得进入下游。
