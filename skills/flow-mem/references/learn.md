# 学习与维护纪律：来源、定域、格式

Workflow A Step 1–4 的细则依据。

## 学习源与范围

内容来源形态（preflight 已做存在性校验，此处只管语义解析）：

- 省略 `--input`：当前整个会话：回顾对话中出现的可复用技术事实（坑点现象与成因、版本行为、绕行方案、验证过的做法）
- 文件/目录路径（可多个）：读取路径下全部内容（典型调用方：flow-dev 收尾传入 `<run-dir>/`、最终报告、reviews 目录）
- 纯文本：文本本身即学习内容

定域（先判切片归属，再在切片内定域）：

0. 切片归属判定：逐条知识点判定它属于哪个切片。可归属到某个框架/库的技术知识（坑点、版本行为、验证过的方案）→ framework 切片；用户表态过的偏好与决策（有纠正、否决、拍板、显性验收等用户在场证据）→ decisions 切片，定域细则见「decisions 切片」章；两者都不符合的不学
1. 以 preflight JSON 的 `project.deps`（dependencies + devDependencies）为框架归属白名单，逐条知识点判定归属哪个包
2. 内容涉及 deps 之外但确属框架/库的包（会话中新引入的依赖、全局工具）→ 同样归属，目录名用其 pkg name；preflight 未抽到 deps（项目无 package.json）时退化为按内容自行判定框架归属。排除：自家可维护仓库的内部技能（flow 技能族 `skills/flow-*` 等）不是外部依赖——其坑点知识的宿主是可直接修改的技能文档，正确动作是把坑点直接优化进对应技能的 SKILL.md / references 并提交（或修复脚本本身），不入知识库；知识库只收不可直接修改的外部依赖的知识，存可修改对象的知识会与技能本体形成双真源漂移
3. 用户纠正的项目结构习惯按所涉框架归属（如 Nuxt 项目的目录约定归 nuxt/），正文写明结构前提使条目自限适用范围；特定任务类型下成立的用户偏好与决策不归框架、归 decisions 切片；与任何框架/任务类型都无关、处处适用的纯偏好归记忆系统，两个切片都不收
4. 其余不可归属的内容不学：任务业务细节属于项目文档，方法论与经验总结属于 flow-distill
5. 定域只回答「归到哪」；能否入库还要过门槛，见下节

monorepo 提示：preflight 从 `--cwd`（默认当前目录）向上取最近的 package.json；工作区根的依赖与子包不同且两者都相关时，可对根目录再跑一次 `--cwd <root>` 合并两份 deps。

## 入库门槛

硬性判据：知识是花费了中间步骤才获得的，且那些中间步骤的内容或产物不属于最终获得的目标——中间步骤被「消耗」掉才换出结论，结论是目标，中间产物不是。

不算门槛（拒收）：

- 先验已知：获得之前就已经知道，没花中间步骤
- 一步可得：一次验证（文档一查即得、跑一下就确认）或一次思考计算（纯逻辑推导）就能拿到——获得之前不知道也算零成本，因为没有消耗
- 无成本转述：道听途说、模型记忆里的想当然，没花核实步骤
- 个例流水：只对本次任务有意义的过程记录（可复用的结论提取入库，流水不入库）

中间步骤消耗的三种典型形态（准入情形）：

- 反复调试：排除了错误方向 A、C、D 才定位真正成因 B。「排除 A/C/D」是被消耗的中间产物——「A 不是成因」的证据不是目标，成因与解法才是；入库时把易误判的弯路写进正文让下一个人直接跳过，正是这类知识的价值所在
- 搜索核实：候选方案逐个比对验证，被弃候选的浏览与比对是中间步骤，活下来的结论附验证依据才是目标，不写「应该如此」
- 用户纠正：AI 自行推导的做法错了、由用户指正，错误推导与纠正过程是中间步骤，结构前提下的做法（目录约定、命名、组织方式）才是目标

可复用性仍是必要条件：下次你或 teammate 再碰同一框架/结构时能直接避坑或取用。门槛与可复用性两条都过才入库；拿不准时不入库——宁可漏收不可滥收，库的信噪比比收录量重要。

零入库是合法结果。候选全部丢弃或跳过、一条未写时流程照常收尾——库已覆盖、或本次经历的都是先验与一步可得的琐碎知识时，零入库恰是门槛在起作用的证据，不代表学习失败。学习不设产出指标：没有「每轮至少入库一条」的隐性要求，迫于产出压力硬学一条比一条不学更有害。禁止反向硬凑：为求产出而放宽门槛写出的条目会稀释信噪比，日后检索命中时还会冒充有效结果误导后来者。

## 增删改查决策流

任何知识点先过门槛、再查后判，搜索走 search.mjs（用法见 search.md），查哪个库与该知识点的切片归属一致（framework 条目查 framework 库，decisions 条目加 `--kb decisions` 查决策库）：

0. 按「入库门槛」逐条判定：不满足准入的候选直接丢弃，不搜索也不入库
1. `--mode h4 --query <主题关键词>` 打标题；命中同名/同义条目则读取完整条目（该 h4 至下一个 h4）
2. h4 不足时 `--mode fulltext --query <关键词>` 确认是否真不存在
3. 逐条判定动作：
   - 新增：确无相关条目
   - 补充：既有条目不完整，在该条目正文追加，不改 h4 标题（标题是检索锚点，改了会让旧搜索词失效）
   - 纠正：既有条目与新证据矛盾，重写正文；改动理由写进 commit message，不写进知识正文
   - 删除：有证据证明条目过时（版本升级移除了该行为、结论被证伪）；文件删空后删文件并同步移除路由
   - 跳过：既有条目已覆盖，不重复记录

## --ask 规划确认

`--learn --ask` 时 Step 0–2 照常执行（全程只读：preflight 与 search.mjs 均无写入），随后输出规划报告并停在确认门，未获用户确认前禁止任何 KB 写入与路由改动。

规划报告格式（终端输出而非知识文件，不受「知识格式纪律」约束）：

- 1 — 新增；framework；/abs/path/nuxt/route-rules.md；h4 标题：反复调试才定位，弯路有复用价值
- 2 — 丢弃；不适用；主题：未过入库门槛：文档一查即得

第二列是目标切片（framework / decisions）；丢弃与跳过不适用切片。

末尾汇总计数（新增 / 补充 / 纠正 / 删除 / 跳过 / 丢弃各几条）；丢弃与跳过同样列出，让用户看见完整判定面而非只见拟写项。

确认门纪律：

- 询问后等待回复；用户确认（含「继续」等口头同意）后才进入 Step 4 落笔
- 用户提出修改意见 → 按意见修订计划；改动较大时重出规划报告再确认
- 用户拒绝或中止 → 停止，报告停在规划阶段，库里不留任何痕迹
- 确认后按报告原样落笔，不再改判动作；落笔中发现计划与事实不符（如目标条目已被并行会话改动）→ 停止并重出报告确认，不即兴扩写
- --ask 是交互模式：flow-dev 等自动调用方不传 --ask（确认门会阻塞收尾）；--search 全程只读，无 --ask 形态

## 知识格式纪律

知识文件（`<pkg>/<topic>.md` 或 `<pkg>@<version>/<topic>.md`）仅由「h4 + 正文 + 空行」的重复单元构成，无 h1、无 frontmatter：

```md
#### router.push 重复导航在 vue-router 4 静默失败
现象：对同一路由再次调用 router.push 不再抛 NavigationDuplicated，而是返回被拒绝的 Promise，未捕获时表现为「点了没反应」。成因：4.x 起导航 API 改为返回 Promise，重复导航按失败处理。正确做法：await push 并捕获 NavigationFailure，或在不需要结果的场景用 router.replace 语义规避。

#### <知识点标题>
<正文>
```

硬规则：

- h4 标题 = 一句话现象或结论，含可检索关键词（包名、API 名、报错名）
- 正文禁止任何强调符（粗体、斜体均不允许），强调依靠选词与语序
- 正文结构按知识类型组织：调试类写现象 → 易误判的弯路 → 真正成因 → 正确做法（弯路是此类知识的价值所在，省掉它条目就退化成文档摘抄）；验证类写候选方案 → 验证过程与依据 → 结论；用户纠正类写结构前提 → 要求的做法 → 原因（用户说明过才写，不代编）；决策类（decisions 切片）写任务背景 → 用户表态 → 决策内容 → 原因（用户说明过才写，不代编）→ 适用范围
- 可含代码示例，不写时效性评论（「目前最新」「截至某年」）
- 条目之间以一个空行分隔

## 版本归属规则

- 跨版本成立的通识 → `<pkg>/<topic>.md`（通用层）
- 特定版本独有的行为（某版本引入、变更或移除）→ `<pkg>@<version>/<topic>.md`；version 取 package.json 的 pkg name + 实装版本（preflight 的 `project.resolved` 字段，缺时读 node_modules/<pkg>/package.json 的 version）
- 拿不准是否版本特定 → 先写通用层；将来出现版本差异证据时再迁移到版本目录，通用层条目改为指向版本目录的路由

## 路由层维护

每个框架目录必须有 `index.md` 路由层，格式同为 h4 + 正文（h4 = 主题名，正文 = 标准 Markdown 相对链接 + 全角冒号 + 一行定位描述；链接文本取目标文件名，路径相对本 index.md 所在目录解析，保证编辑器内可点击跳转）；决策主题目录（`decisions/<task-type>/<topic>/`）同样必须有 `index.md` 路由层，格式相同：

```md
#### 响应式
[reactivity.md](./reactivity.md)：响应式丢失、解包规则、ref 与 reactive 取舍

#### 版本特定知识
[index.md](../vue-router@5.2.0/index.md)：该版本路由层（存在版本目录时才列）
```

- 版本目录的 `<pkg>@<version>/index.md` 必须同时指向通用层：用一个「通用知识」h4 反向路由到通用层 index.md（如 `[index.md](../image/index.md)：跨版本通用知识路由层`），保证沿版本检索不漏通识
- 新建知识文件时同批补路由；删除文件时同批删路由；路由目标失效（指向不存在的文件）视为知识库损坏，发现即修

## decisions 切片

收「用户表态过的任务型偏好与决策」：特定任务类型下成立、有用户在场证据锚定的做法约定。与 framework 切片互补——framework 回答「这个框架/库怎么用才不踩坑」，decisions 回答「这类任务用户要的是什么」。

目录结构：

```text
references/decisions/<task-type>/<topic>/{index.md, <task-context>.md}
```

- `<task-type>`：任务类型，kebab-case，按任务形态归类（如 demo-replica、verification）；定域时与 preflight 的 `kb.decisionTypes` 交叉，已有类型优先复用，确无匹配才新建
- `<topic>`：决策主题目录（如 asset-strategy），同一主题下不同任务产生的决策累积于此
- `index.md`：主题目录的路由层，格式同 framework 路由层（h4 = 主题名，正文 = 相对链接 + 全角冒号 + 一行定位描述）
- `<task-context>.md`：任务上下文知识文件，以产生该决策的任务命名（如 `260731-my-room-3d-tour-redo.md`）；同主题的多个任务上下文并存，新决策追加新文件而非改写旧文件；旧决策被新证据推翻时按「纠正」动作重写对应条目正文

入库门槛（在通用入库门槛之上叠加）：

- 用户在场证据是必要条件：决策必须由用户的明确表态锚定——纠正（做法被指正）、否决（产物或方案被否）、拍板（候选中选定）、显性验收（产物被采纳、称赞、并入主干）
- 默许不算证据：用户未反对不等于表态；推断「用户应该会喜欢」是无成本转述，不入库
- AI 自行推导且未经用户确认的做法不归本切片：够技术门槛的归 framework，方法论归 flow-distill
- 通用门槛同样适用：只对本次任务有意义的琐碎安排（个例流水）不入库

正文结构：任务背景 → 用户表态 → 决策内容 → 原因（用户说明过才写，不代编）→ 适用范围（哪个任务类型下成立；不适用面写清边界）。

格式样例：

```md
#### 复刻类 demo 优先迁移真实资产，风格化重建在视觉验收下必败
任务背景：……用户表态：第一轮产物被「效果不好」否决，第二轮被采纳。决策：……原因：……适用范围：复刻/对照测试类 demo；对外发布场景另行评估。
```

检索约定：列任务类型用 `--mode decisions`；标题与全文检索加 `--kb decisions`（见 search.md）。
