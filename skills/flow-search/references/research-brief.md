# 深度研究需求澄清手册

由 SKILL.md Workflow C Step 1 调起。定义深度研究分支的需求澄清阶段：三层 Ask 框架、研究模式分类、智能跳过与逃生舱口、提问质量纪律，以及 brief.yaml 产出规格。

搜索质量的上限在搜索开始前就决定了。宽泛主题直接开搜，返回的多半是噪声；前期 2–3 分钟的结构化澄清，省掉的是后期 20 分钟的无效迭代。

## Ask 调用约定

每次 AskUserQuestion 调用遵循四件套（方法论源自 YC Office Hours 提问框架），映射到结构化工具 API：

- **Re-ground**（落点 Ask 调用前的纯文本导语）：1–2 句声明当前项目/分支/任务与进度，让用户知道自己在回答什么上下文里的问题
- **Simplify**（落点 question 措辞）：用 16 岁能懂的语言，避免内部术语，给具体例子
- **Recommend**（落点首个选项）：label 尾部加「(Recommended)」，description 写一行理由；选项的 description 附完整度与 effort 估算 `(human: ~X / CC: ~Y)`
- **Options**（落点 options 数组）：label 1–5 词；互斥单选用多选项，可叠加的用 `multiSelect: true`

示例（研究目标分类问法）：

- 导语：「**当前项目：** my-app | **分支：** feature-search。你要求调研 React 19——想确认的是变化全貌和升级成本。」
- question：「这次调研想达到什么程度？」
- 首选项：label「全面调查 (Recommended)」，description「升级决策需要完整利弊分析。Completeness 10/10，human ~1d / CC ~20min」
- 其余项：「标准研究」「快速概览」，同样附完整度与 effort。

## 三层框架

### 第一层：项目重述（Re-ground 确认）

先确认理解无误再往下走：复述用户原始请求 → 提炼核心主题 → 问「是这样吗？」（选项：确认开始 / 需要澄清）。

跳过条件：用户请求已足够具体（含明确对象、范围、产出形态），或用户已表达过紧迫感。

### 第二层：研究目标分类

- 验证假设（有具体想法，找支持/反对证据）：映射模式 focused
- 对比决策（在几个选项间做选择）：映射模式 focused
- 探索未知（对领域不了解，要系统概览）：映射模式 scan
- 追踪最新（了解最新进展、版本、趋势）：映射模式 scan
- 深度调查（全面收集，形成完整认知）：映射模式 comprehensive

跳过条件：请求措辞已暴露模式（「快速了解」→ scan、「深入调研」→ comprehensive、「验证一下」→ focused）。

### 第三层：模式专用提问（一次只问一个）

**focused（验证假设 / 对比决策）：**

- Q1 具体假设是什么？一句话陈述预期结果 — 自由陈述（示例：「App Router 比 Pages Router 慢 20% 以上」）；用户已给对比列表则跳过
- Q2 什么证据会让你改变想法？（反证标准） — 官方基准即可 / 多个独立来源一致 / 要看到实际代码案例
- Q3 范围边界 — 窄（特定版本/场景）/ 中（含相关生态）/ 宽（历史演变+未来趋势）

**scan（探索未知 / 追踪最新）：**

- Q1 当前了解程度 — 完全新手（要基础概念）/ 有一定了解（知道主要术语）/ 很了解（关注最新与边缘案例）
- Q2 时效要求 — 仅最新（近两年）/ 包含历史演变 / 质量优先不限
- Q3 输出形态 — 执行摘要（2–3 段）/ 结构化对比表 / 详细报告（带引用与置信度）/ 原始发现清单

**comprehensive（深度调查）：**

- Q1 研究深度 — 快速概览（1 轮）/ 标准（2–3 轮循环）/ 穷尽（最多 4 轮直到达标）
- Q2 置信度要求 — 高（多源交叉验证，矛盾必须解决）/ 中（主流来源可信即可）/ 低（方向性信息即可）
- Q3 特殊角度（multiSelect） — 负面评价/已知限制 / 中文资料/国内实践 / 学术论文/权威研究 / GitHub Issues/真实反馈 / 无需特殊角度

## 智能跳过规则

只问答案尚不明确的问题：

- 「快速了解一下」：跳过目标分类；默认 scan
- 「深入调研」：跳过目标分类；默认 comprehensive
- 「验证这个想法」：跳过目标分类；默认 focused
- 「只要最新信息」：跳过 scan 的 Q2；默认 latest-only
- 已给完整对比列表：跳过 focused 的 Q1；默认用用户列表
- 已说明输出形态：跳过输出类问题；默认用用户指定

## 追问矩阵

用户答案不够具体时，按下表追问（**推一次，再推一次**，直到具体可执行）：

- 模糊/宽泛：范围澄清 — 「这个词会返回海量结果。具体是哪个方面/场景？」
- 无成功标准：质量阈值 — 「什么算'找到答案'？高=多源验证 / 中=主流来源 / 低=初步了解」
- 无输出偏好：输出形态 — 「要 3 句话摘要、详细报告、还是原始发现列表？」
- 无时间边界：时效要求 — 「信息需要多新？1 周内 / 1 月内 / 1 年内 / 不限？」
- 无失败条件：停止条件 — 「什么情况算'没找到'？什么时候可以停止？」

## 逃生舱口（Escape hatch）

用户第一次表达不耐烦（「直接搜」「跳过这些问题」）：承认成本，给出可控降级选项——

- 导语说明：这些问题多花 2–3 分钟，但决定搜索质量；快速模式会用合理默认值立即开跑，之后可要求深入。
- 选项：快速模式（完整度 6/10）/ 继续问完 (Recommended)（完整度 10/10）。

用户第二次表达不耐烦：尊重选择，直进步骤 2，默认配置：scan 模式 / 质量阈值 medium / 执行摘要 / 执行档位 easy（无深度信号的默认档）。

## 提问质量原则

### 反奉承禁用词

- 「这是个有趣的问题」：直接说难点在哪
- 「有很多方式可以思考这个」：选一种并说明理由
- 「你可能会考虑…」：说「应该…」并说明原因
- 「这可以工作」：说「这能/不能工作，因为…」

### 追问纪律

- 第一个答案通常是包装过的版本，真实答案在第二、三次追问之后。
- 命名常见失败模式帮用户自检：「搜索词太宽泛」「没有明确目标」「缺少时效约束」。

### BAD vs GOOD

用户说「搜索 LLM 评估框架」：

- ❌ 「好的，我来搜索 LLM 评估框架的最新信息」
- ✅ 「LLM 评估框架是个大领域，数百个结果。需要缩小范围：比较主流框架（RAGAS/TruLens/DeepEval）？找特定任务的评估（代码生成/数学推理）？还是了解方法论（自动 vs 人工评估）？」

## 产出：brief.yaml

澄清结束，按用户回答生成需求文档，写入 `/tmp/flow-search/{YYYY-MM-DD}/{task-name}/brief.yaml`：

```yaml
研究目标: {提炼后的目标}
研究模式: {focused/scan/comprehensive}
背景水平: {beginner/intermediate/expert}
质量阈值: {high/medium/low}
时效要求: {latest-only/history-ok/none}
输出格式: {summary/comparison-table/detailed-report/raw-findings}
特殊角度: [negative, chinese, academic, github-issues, none]
反证标准: {string，focused 模式必填}
范围边界: {narrow/medium/wide}
```

此文档驱动 eval-loop 的查询集群构建，并注入评估器提示词（评估器据此判定时效扣分与角度覆盖）。`{task-name}` 用 2–4 个词的 kebab-case 主题概括（如 `llm-eval-frameworks`）。

## 注意事项

1. **不要直接开搜**：跳过澄清的搜索，质量上限就是查询词本身的质量
2. **一次只问一个问题**：批量提问会让用户跳过不想答的项
3. **跳过要有依据**：只跳过请求中已明确回答的问题，不靠猜测默认
4. **紧迫感要尊重**：逃生舱口触发两次后不再挽留，用默认配置直跑
